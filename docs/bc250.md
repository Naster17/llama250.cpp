# BC-250 (gfx1013) optimization log

Everything measured on real BC-250 boards (Alpine Linux, RADV, 40 CU unlocked),
November 2026. Model for all single-board numbers: LFM3-1.7B (24 layers, hybrid
shortconv + 6 GQA attention layers, n_embd 2048, ffn 7680, 256k ctx), Q8_0 unless
noted. Flags: `-ngl 99 -t 6 -fa 1 -ub 512`, 3+ repetitions, 2000 MHz, < 75 C.

## 1. Hardware facts (verified, not assumed)

| Claim | Verdict | Evidence |
|---|---|---|
| No cooperative matrix / WMMA | confirmed | vulkaninfo: no coopmat properties; ggml: `matrix cores: none` |
| No accelerated int8 dot product | confirmed | all `integerDotProduct*Accelerated = false`; ggml: `int dot: 0` |
| Packed FP16 is the compute path | confirmed | q8_0 GEMM reaches 10-12 TFLOPS, above the 7.7 TFLOPS FP32 peak |
| 40 CU unlock active | confirmed | `RADV_DEBUG=info`: `num_cu = 40`, all `cu_mask = 0x3ff` |
| Wave32 | confirmed | ggml: `warp size: 32`; forced via subgroup size control |
| UMA, single DEVICE_LOCAL heap | confirmed | vulkaninfo: 1 heap, 15.3 GiB, `rebar: 1` |
| No VGPR spills in GEMM/FA shaders | confirmed | `RADV_DEBUG=shaderstats`: zero spilled VGPRs (Q8_0 and Q4_0) |
| mclk/socclk/fclk can drop between batches | refuted | each exposes exactly one DPM state (450/1254/450 MHz); nothing to lock |

Roofline: ~357 GB/s GDDR6, ridge ~10 FLOP/byte. Prefill of small dense models is
compute-bound; decode is bandwidth-bound (Q8_0 tg128 ~ 284 GB/s effective).

Upstream drift alone gave +11-18% prefill between the two commits; the BC250 tuning

| ub | 128 | 256 | 512 | 1024 | 2048 |
|---|---|---|---|---|---|
| tok/s | 2146 | 2561 | **2753** | 2518 | 1878 |

512 is the sweet spot. Bigger is NOT better on this chip (-32% at 2048).

### Quant formats (corrected numbers, see note)

| Quant | pp512 | pp2048 | tg128 | file |
|---|---|---|---|---|
| Q8_0 | 2826 | 2838 | 155.2 | 1.71 GiB |
| Q4_0 | **2906** | ~2900 | **212.9** | 0.97 GiB |
| Q4_K_M | 2560 | 2583 | 211.0 | 1.02 GiB |

Q4_0 wins overall: prefill on par with Q8_0 (half the weight bytes offset the dequant
cost), decode +36%. K-quants cost ~9% prefill vs Q8_0 (nested-scale unpack overhead).

NOTE: an earlier benchmark window reported Q4_0 prefill at 1169 tok/s (2.2x slower
than Q8_0). That was a transient system state: the exact same files, commands and
builds later reproduce 2900+ across all three builds, and per-op profiling agrees
(q4_0 GEMM 12.0 TFLOPS vs q8_0 10.3). The "Q4 prefill is slow" conclusion is
retracted. The q4_0 GEMM shader already uses packed uint16 loads + unpack8
(`mul_mm_funcs.glsl`), so the proposed byte-to-uint16 rewrite had nothing to fix.

### KV cache type

q8_0 KV vs f16: pp2048 2739 vs 2753 (neutral), tg @ d4096 144.4 vs 148.2 (-2.5%).
Keep f16.

### Load mode / mmap

Upstream sets `mmap_support = !is_integrated_gpu`, so AUTO meant **no mmap** here.
Measured: `-lm mmap` pp512 2747 vs auto/none 2517 (+9-12%). Patched: AUTO resolves
to mmap when ReBAR is present; verified auto == mmap after the patch (2826).

## 3. Two-board RPC cluster (1 GbE, MTU 1500, layer split)

Baseline: cluster is slower than one board for models that fit on one board
(pp512 ~1994 vs 2826, tg ~123 vs 155) - pipeline bubble + wire latency. Clusters pay
off for models that do not fit. `-sm row` fails: RPC backend has no split buffers.

### BF16 wire patch (GGML_RPC_WIRE_BF16=1)

F32 activations >= 64 KB crossing the split boundary are converted to BF16 on send,
expanded on receive (both directions). Weights untouched.

| Test | F32 wire | BF16 wire | delta |
|---|---|---|---|
| pp2048 ub256 | 2212 | 2558 | +15.7% |
| pp2048 ub512 | 2351 | 2733 | +16.3% |
| pp512 | 1855 | 2166 | +16.8% |
| tg128 | 123.9 | 124.3 | ~0 (8 KB/token < threshold) |

Client rx traffic halved exactly (70.5 -> 35.4 MB per pp2048 run). With BF16, cluster
pp2048 (2733) matches single-board (2753): the network penalty on prefill is gone.
Greedy generation (llama-server, temp 0, 40 tokens): byte-identical F32 vs BF16.

### TCP_QUICKACK (GGML_RPC_QUICKACK=1)

+0.5-0.8% pp2048, noise elsewhere. TCP_NODELAY is already set on both sides
(`transport.cpp`), which prevents the 40 ms Nagle/delayed-ACK stall. Kept gated, off
by default.

### Other RPC findings

- Weight hash cache (`-c`) only caches tensors >= 10 MB; LFM3's smaller tensors
  re-send ~155-205 MB on every model load. Lowering HASH_THRESHOLD would help.
- RPC traffic crosses the network only at device split boundaries (once per ubatch
  with `-sm layer`), NOT per layer.
- The all-reduce path (row split) already auto-casts F32 -> BF16 upstream
  (`wire_bf16` in ggml-rpc.cpp), but row split itself is unsupported over RPC.
- ub sweep on cluster: ub256 most stable (2229), ub128 worse (1844).

## 4. Governor and cold start

cyan-skillfish-governor-smu, SMU method, config `/etc/cyan-skillfish-governor-smu/config.toml`.
Idle 1000 MHz; ramp to 2000 MHz takes ~1.2 s from idle. llama-bench absorbs the ramp
in its warmup iteration (verified: no drop even with MESA_SHADER_CACHE_DISABLE=1).
The first request after boot/idle on a cold Mesa cache can catch the ramp; for
llama-server latency, proposed config (root required):

```toml
[timing.intervals]
adjust = 50_000      # was 200_000
[timing]
burst-samples = 10   # was 60
[frequency-range]
min = 1500           # was 1000 (optional; costs idle watts)
```

The governor exposes DBus `com.cyanskillfish.Governor` (runtime freq range), but on
root's session bus. mclk/socclk/fclk have single DPM states - nothing to lock there.

## 5. Things that turned out to be placebo

- mimalloc instead of musl mallocng: A/B with LD_PRELOAD, +0.15% (noise). Steady-state
  inference reuses buffers; the allocator is not on the hot path.
- RADV_PERFTEST=sam: zero effect (ReBAR already on, UMA).
- RADV_PERFTEST=nggc / mesa_glthread: graphics/OpenGL-only, irrelevant to compute.
- transfer_queue: one queue family on this device, no SDMA queue to offload to.
- "Dozens of small command submits": the graph is one command buffer; descriptor
  writes are cached and skipped when bindings are unchanged (ggml-vulkan-common.h).
- Push descriptors: not used, but the descriptor-reuse cache already removes the
  per-dispatch update cost in steady state.

## 6. Mesa version and kernel: what actually moves the needle

Mesa's ACO compiler emits materially better code between 25.2 and 26.1. Forced-recompile
shader stats (RADV_DEBUG=shaderstats, MESA_SHADER_CACHE_DISABLE=1), same SPIR-V:

| Shader | VALU insns 25.2 -> 26.1 | other |
|---|---|---|
| FA (2 variants) | 5574 -> 3844 (-31%) | est. latency -14% |
| GEMM pair | 6035/6065 -> 5323/5383 (-12%) | |
| big-tile shader | VGPRs 164 -> 96 | code size -24% |
| matvec | 1970 -> 1862 | VGPR 40 -> 36, waves/SIMD 24 -> 28 |

Keep Mesa current. Alpine 3.24 ships 26.1.6 (latest stable at the time of writing;
26.3.0 was staged in the unreleased 3.25 branch). Both boards were upgraded to 26.1.6.

### The board-to-board gap: GPU clock-holding + CPU boost, not Mesa

An early comparison attributed the .104-vs-.105 gap to Mesa, then to the kernel. Both
were incomplete. After upgrading BOTH boards to Mesa 26.1.6, shader codegen is
byte-identical (0 differing fields across all 25 shaders), VBIOS is identical
(113-AMDRBN-003), SMU firmware is identical (88.6.0), and GPU/mem/fabric clocks match.
Yet .104 pp2048 ~2570 vs .105 ~3070. The real causes on .104:

1. **GPU load detection is broken.** The governor reads `load 0.00 status -5` (both
   `busy-flag` and `process` methods, both old and new governor binaries, on r2 and r3).
   It cannot see GPU load, so it keeps the GPU near idle clock instead of holding 2000.
   Forcing `[frequency-range] min = 2000` makes the isolated GEMM jump from ~6200 to
   **10912 GFLOPS** (higher than .105's 9800) - proof the GPU silicon is fully capable.
2. **CPU boost does not sustain.** Under load .104's CPU sits at ~1396 MHz while .105's
   holds ~3194 MHz. The full-model prefill is partly CPU-dispatch-bound, so even with the
   GPU forced to 2000 the full model stays ~2570 until the CPU boosts. The SMU-OC tool
   sets the boost ceiling (`q3_0x8f_set_max_cpu_boost_clk 3500`) but .104's SMU P-state
   algorithm does not raise the CPU under load with the current `scale = -19` config.

So the gap is board-specific SMU behavior (GPU load reporting + CPU P-state boost), not
Mesa, shader code, kernel version, VBIOS, or silicon capability.

**Fixes applied to .104 (2026-11-15):**
- SMU-OC venv repaired: the distro upgrade bumped Python 3.12 -> 3.14, breaking the venv
  (`No module named bc250_apply`). Symlinked `.venv/lib/python3.14 -> python3.12` (pure
  Python, no C extensions). Service now applies at boot.
- Governor: .105's newer binary is installed; its load detection also reads `status -5`
  on .104, so the config uses `busy-flag` with `min = 2000` to hold the GPU clock.

**r3 is now the PERSISTENT default on .104.** r3 blacklists amdgpu at boot and arms a
240 s boot guard that reverts unless ACKed, so a boot service was added to do the GPU
bring-up automatically:
- `/usr/local/bin/bc250-r3-gpu-ready.py` + `/etc/init.d/bc250-r3-gpu-ready` (default
  runlevel): waits for the guard to arm, `modprobe amdgpu`, applies SMU-OC, restarts the
  governor, then ACKs the guard (only if amdgpu loaded, so a failed load still falls back).
- `GRUB_DEFAULT=bc250-rocm-r3-7.2.10-trial` in `/etc/default/grub`, grub.cfg regenerated.
  Backups: `/etc/default/grub.bak-r2default`, `/boot/grub/grub.cfg.bak-r2default`. The r2
  entry remains in the GRUB menu as a manual fallback.
- Governor `[frequency-range] min = 2000` holds the GPU clock (load detection reads
  `status -5` on .104, so the governor cannot ramp on its own).
Verified across reboots: r3 boots, amdgpu loads, guard ACKed, 40 CU, benchmark runs.

**GPU side - SOLVED in software:** boot r3 (custom `updates/amdgpu.ko.gz`), ACK the boot
guard, `modprobe amdgpu`, restart the governor after amdgpu loads, and set
`[frequency-range] min = 2000`. With this, .104's per-op GPU times become byte-for-byte
equal to .105 (GEMM m=7680 ~10750 GFLOPS, pp512 op-sum 164.6 ms vs .105 165.3 ms).

**Remaining gap - NOT fan, NOT CPU frequency (both disproven):** an earlier fan/cooling
hypothesis was wrong (fans are identical; .104 is not hotter under sustained load). After
the GPU fix, a ~30 ms per-graph dispatch overhead remains on .104 (pp512 wall 194 ms vs
.105 164 ms, while the GPU op-sum is the same ~165 ms on both). Exhaustive matching:

| Variable | .104 | .105 |
|---|---|---|
| GPU gfxclk under load | 2000 | 2000 |
| CPU freq (forced OC 0x25, all cores) | 3493 sustained | 3493 |
| CPU mem latency (idle + under GPU load) | 135.8 ns | 135.8 ns |
| amdgpu build-id | b97bca56... | b97bca56... |
| libggml-vulkan / base md5 | identical | identical |
| SMU features / P-states / gpu_metrics fmt | identical | identical |
| VBIOS / SMU fw | 113-AMDRBN-003 / 88.6.0 | same |

Forcing the CPU to a sustained 3493 MHz (per-core OC clock `q3_0x25`) does NOT close the
gap, so it is not CPU boost/frequency. Memory latency, driver, builds, clocks all match.
The residual ~16% is a board-level hardware difference (GPU front-end / command-processor
or CPU dispatch efficiency) not exposed by any of these metrics. OC clock was reverted
(`q3_0x26`) since it gave no benefit. Do NOT raise CPU frequency without the matching
undervolt - the tool README warns this can permanently brick the board.

## 7. Known issues

- `llama-cli` + RPC offload segfaults during model load (any model, with or without
  the fork patches). `llama-bench` and `llama-server` work. Upstream bug.
- RPC `-sm row`: "device RPC0 does not support split buffers".
- LFM3 default ctx is 262144; pass `-c` explicitly to tools that allocate it.

the boards). Key commands:
