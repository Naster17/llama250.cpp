## 3. Live verification runs done for this research

Purpose: check whether upstream RPC pipeline parallelism (#18626, merged) actually helps the
2-board cluster on the CURRENT build (Nov-15 cluster numbers predate the upstream merge).

Run 1 (2026-11-19, both boards idle, governor pinned 2000):

```sh
# .105
~/llama250.cpp/build/bin/ggml-rpc-server -H 0.0.0.0 -p 50052 -t 6 -c
# .104
GGML_RPC_WIRE_BF16=1 ~/llama250.cpp/build/bin/llama-bench \
  -m ~/models/LFM3-1.7B-Q8_0.gguf -ngl 99 -fa 1 -ub 256 -p 2048 -n 128 -r 2 -t 6 \
  --rpc 192.168.1.105:50052 -sm layer
```

Result: pp2048 = 2604.90 +/- 20.19 t/s, tg128 = 129.48 +/- 0.58 t/s.
(vs Nov-15 old base: 2558 / 124.3 -> +1.8% / +4%. No pipeline-parallelism jump.)

Run 2 (same setup, `-p 512 -n 0 -r 1 -v`):

```
llama_context: pipeline parallelism enabled
sched_reserve: graph: nodes = 998, splits = 5, input objects = 4, input tensors = 13
pp512 = 2305.73 t/s
```

Conclusion: **pipeline parallelism ENABLES on the current build; its benefit scales with
per-ubatch compute.** LFM3 (small per-ubatch compute): pp2048 2605 vs 2753 single-board -
no help. gemma4-26B (large per-ubatch compute, step-2 bench): pp2048 1085 vs 852
single-board - **+27%, PP works there**. Root cause of the residual gap is code-visible
(sec. 6.1): RPC has async graph compute + events, but `cpy_tensor_async = NULL`, so
split-boundary activation copies fall back to the sync path which synchronizes BOTH
backends. On CUDA (async copies) the same mechanism measured +30-70% pp with 2 devices
(PR #18626 comments). Implementing async RPC copies remains the biggest RPC lever.

Peer server stopped after each run (`pkill -x ggml-rpc-server`); boards left idle.

1. **patches/README.md "Companion driver patch" section still recommends the RETRACTED
   int-dot Mesa patch** ("~4.3x MoE matvec, +30% prompt processing"). That claim was

   Pro hardware). Anyone following that section gets silently wrong outputs. DELETE it.

   (verified on both boards). Fix the text or buy the NICs (sec. 6.2).
3. docs/SCENARIOS.md "6 Zen2 cores / 12 threads" and scripts/llama250.sh THREADS=10 -
   the boards run 8c/16t (core unlock active). Sweep -t 12/14/16.
4. Board git trees: HEAD 0b5c32d + 121-file uncommitted diff. Commit/sync to local master
   bac6c3779 so what is built matches what is recorded.
5. scripts/rpc-server.sh: add `-c` (weight hash cache). Without it every model load
   re-transfers the full split over 1 GbE (~105 s for flint's ~11.6 GiB half).
6. Do not let SkillFishOS's vkpeak "45,495 GIOPS int8 dot" number reopen the int-dot
   question: with the extension absent vkpeak computes dots in software; the silicon
   opcodes are dead (sec. 8).

## 5. Single-host opportunities (ranked)

### 5.1 Speculative decoding - the biggest untouched tg lever for dense models

Fully in tree and never benchmarked on BC-250 in any fork log. Implementations available
(common/common.h:176-190, common/speculative.cpp ~3300 lines): draft-simple, EAGLE3,
draft-mtp (native MTP heads, chain_heads for multi-layer MTP, speculative.cpp:1793+),
DFlash, DSpark, DFlash2, LiliCorr, n-gram self-speculation (simple/map_k/map_k4v/mod/cache).

Why it should shine on this chip: verification of 8-16 draft tokens costs pp-time, and pp
is ~33x faster than tg here (2800 vs 85 t/s class). Upstream reports 2-3x for EAGLE3
(PR #18039). The 4claps production BC-250 cluster runs `--spec-type draft-mtp
--spec-draft-n-max 3 --no-spec-draft-backend-sampling` on Qwen3.6-35B-A3B at 51.7 t/s over
2 boards - proof the pattern works on this silicon class.

Ready pairings for the local zoo:

- gemma-4-26B-A4B <- RedHatAI/gemma-4-26B-A4B-it-speculator.eagle3 (listed in docs/speculative.md).
- Qwen3-8B-class / Qwen3-VL-8B <- AngelSlim/Qwen3-8B_eagle3, Tengyunw/qwen3_8b_eagle3.
  EAGLE3 hooks for qwen3.5/3.6 hybrids already merged (b14e3fb90 #24593, 51a77c4f2 #32589).
- Qwen3.5-35B-A3B: the local unsloth GGUF has NO nextn layers (header-verified) -> use a
  small dense draft (qwen3.5-2b-f16.gguf is already on the board, same tokenizer family)
  or an EAGLE3 draft if published. Alternatively re-convert with MTP weights if the HF
  checkpoint has them (llama_model_n_layer_nextn / LLM_KV_NEXTN_PREDICT_LAYERS supported).
- n-gram self-speculation (--spec-type ngram-simple): zero extra memory, good for
  code/repetitive agent output.
- SenseNova-Loop: MTP conversion + decoding already merged upstream; draft-mtp is the
  natural next step for TTS tg (21.7 t/s today).

Known Vulkan spec-decode hazards, ALL fixed in the merged base (verified in tree):
#30695 multi-device decode regression (fix a8d9a7e1e #30468 after e0bcacc #29741),
#28060 checkpoint-restore livelock (closed), #25666 AMD MMVQ on spec steps (merged),
#29418 MTP + tensor-split assert (watch item if combining MTP with -ot overrides).

Risks: memory (draft + target + PP 4-copy buffers on 15.2 GiB), acceptance-dependent gains,
MoE verification reads all routed experts for the whole draft batch (bandwidth scales with
draft length - sweep --draft-max 4/8/16). Verify: llama-bench tg + greedy-output identity,
then server timings.predicted_ms.

Memory feasibility (the "we already run models at the memory limit" objection):

Speculation does NOT always need a second full model. Three cost tiers:

1. ZERO extra weights: n-gram self-speculation (--spec-type ngram-simple / ngram-mod).
   Drafts come from n-gram matches in the existing context; only a bounded lookup cache
   (tunable: --spec-ngram-mod-n-min/n-max/n-match, lookup_cache_static/dynamic,
   arg.cpp:1611-1618,4339-4360). Works on ANY model, including the at-limit ones.
2. NEAR-ZERO: draft-mtp uses nextn/MTP heads ALREADY INSIDE the target GGUF (one extra
   layer, ~0.1-0.3 GiB for h2048). Requires an MTP-bearing GGUF: the local Qwen3.5-35B-A3B
   unsloth file has none (header-verified); unsloth publishes -MTP variants, or re-convert
   with MTP weights. This is what 4claps runs in production at 115k ctx on 2 boards.
3. SMALL draft: EAGLE3 is ONE transformer layer + (optionally reduced-vocab) head, not a
   second model. Measured HF sizes: AngelSlim/Qwen3-8B_eagle3 = 799 MB f16 (~0.45 GB Q8_0
   GGUF); RedHatAI/gemma-4-26B-A4B-it-speculator.eagle3 = 1.86 GB f16 (~1.0 GB Q8_0,
   ~0.6 GB Q4_K). Draft KV is tiny (1 layer); target KV unchanged; the verify batch adds
   n_draft+1 tokens of compute buffer, not KV.

Placement/size knobs: --spec-draft-ngl/-ngld (arg.cpp:4302, draft layers on CPU),
--spec-draft-override-tensor/-otd (arg.cpp:4171, pin draft tensors to a device - on RPC keep
the draft entirely on the client board or the CPU backend), draft quantization (Q8_0/Q4_0),
EAGLE3 reduced draft vocab (d2t). UMA caveat: -ngld 0 does NOT save physical memory (CPU
and GPU share the same GDDR6); the real savings are draft quant, reduced vocab, MTP, ngram.

Conclusion: the 1.5-3x tg prize is on the models WITH headroom (8B class, LFM3, Loop);
the at-limit models get ngram/MTP only, and their main levers are the other sections
(5.2-5.6: tiles, staging, quant, REAP). Do not plan a full second model for the tight cases.

Expected: 1.5-3x effective tg on dense chat [INFERENCE from upstream 2-3x claim, discounted
for acceptance and draft cost].

Key lessons:

- **Draft/target lineage matters more than draft size.** The gemma4 EAGLE3 draft is
  lineage-mismatched (QAT target). A matching draft (non-QAT target, or QAT-trained
  speculator) is required before EAGLE3 can win here.
- **ngram-mod is the only zero-cost win today**, and only for repetitive/code/agent
  output; free prose gets nothing. --spec-type ngram-mod, no -md, no extra memory.
- **Serving tg != bench tg**: server adds per-token sampling/detokenize/HTTP on the
  nerfed-FPU Zen2 (gemma4 47.8 serving vs 92.8 bench; LFM3 79 vs 155). A/B pairs are
  internally consistent; absolute serving numbers are the server ones. This CPU
  per-token overhead is itself a future lever (GPU sampling / leaner sampler chain).
- **Memory wall**: OS-visible RAM is 14.86 GiB (16 GiB physical minus ~1.1 GiB
  carveout). dio pins weights there; model + draft + KV + compute must stay under it.
  gemma4+EAGLE3 only fits at c1024/ub128; OrcaSAQ does not fit at all.
- **Zombie servers**: llama-server stuck on a dead RPC peer ignores SIGTERM and holds
  GPU memory; two such zombies caused a chain of OOM load failures. kill -9 strays
  before big loads; check `pgrep -x llama-server` when loads start failing.
- ub2048 device-losts on gemma4 (pre-existing); MoE pp sweet spot is ub1024 (sec 5.2).

### 5.8 Serving generation: write-combining logits fix (GGML_VK_HOST_MALLOC_CACHED) - LANDED

**The biggest single win of this research: serving tg 47.8 -> 88.3 (+85%) on gemma4-26B.**

Diagnosis chain (all measured on .104):

- llama-bench tg (no sampling) = 92.8 t/s; llama-server tg = 47.8; llama-cli tg = 47.4
  -> overhead is in the shared decode+logits+sampling path, not HTTP/slots.
- Per-token harness (decode-logits-bench.cpp): decode 3.4 ms (graph build+submit),
  logits wait 8.1 ms (GPU), **memcpy of the 1 MB logits row = 9.9 ms (~100 MB/s)**,
  argmax on a cached copy = 1.0 ms.
- Cause: RADV/gfx1013 exposes NO HOST_CACHED memory types (vulkaninfo: 0). All
  host-visible buffers are write-combining; CPU reads of GPU-written WC run at
  ~100 MB/s. The logits buffer (vocab 262144 x 4 B = 1 MB/token) is read by the
  sampler every token -> ~10 ms/token pure memory-path overhead.
- movntdqa (SSE4.1 non-temporal loads) streams WC at **4.8 GB/s** (wc-copy-bench.cpp:
  memcpy 106 MB/s vs nt_copy 4821 MB/s, 45x).

Fix (patch 0019, two parts):

1. ggml_vk_memcpy_from_wc: NT-load copy for staging->host reads (target("sse4.1")
   attribute + __builtin_cpu_supports runtime check; ggml-vulkan is not built with
   -march=native). Applied to all out_memcpys execution sites.
2. GGML_VK_HOST_MALLOC_CACHED=1: ggml_vk_host_malloc uses cached malloc + register
   (the multi_device path) instead of WC vkAllocateMemory, and the AMD host-import
   gate is lifted under the same env. Output buffer lands in cached RAM; GPU copies
   logits into it (import or staging+NT), CPU samples at full speed.

Part attribution (verified 2026-11-20 on upstream master b94959a64): the serving tg
fix is part 2 ONLY. buf_output uses the device host buffer type, so the sampler reads
logits directly from the WC buffer - no staging/out_memcpys involved (instrumented:
zero staging copies for the logits row). NT-only serving tg = 47.6 (fork, no env) /
48.2 (upstream+NT) vs 47.0 vanilla upstream. Part 1 (NT) speeds the staging paths:
RPC GET_TENSOR on the peer, explicit tensor_get, and the import-failure fallback.

Measured (gemma4-26B-A4B Q4_K_XL, q8_0 KV, .104):

| Config | pp512 | pp2048 | bench tg128 | server tg |
|---|---|---|---|---|
| baseline | 932 | 852 | 92.8 | 47.8 |
| HOST_CACHED=1 | 936 | 904 (+6%) | 91.5 | **88.3 (+85%)** |
| RPC 2-board, no fix | - | - | - | 44.0 |
| RPC 2-board, fix on both nodes | - | - | - | **72.9 (+66%)** |

Greedy output identical. Launcher sets HOST_CACHED=1 by default (0 disables).
All launcher knob combos verified (CACHE 0/1 x MMID_TUNE 0/1): load 31 s, tg 87.5-88.3.

Notes:

- One "host memory import failed, using staging" warning at startup is benign: the
  staging+NT path is also fast (0.22 ms per 1 MB copy).
- The AMD import exclusion exists because amdgpu re-faults imported pages on each
  submission; with the small output buffer this cost is not visible (pp improved).
  If large host allocations regress on other models, set HOST_CACHED=0.
- LLAMA_OUTPUT_CPU_BUF experiment (cached output buffer without the import path)
  was reverted: alone it left the staging copy slow; the cached-host env is the fix.
- Sporadic load stalls/deaths observed during the session (CLI fit-params segfault,
  transient server load stalls) - unrelated to this fix; the fit-params segfault is
  an upstream gemma4 MoE bug in the probe context (workaround: -fit off).

### 6.4 Row-split / split-buffers over RPC (the big one, after 6.1 + 6.2)

Still unimplemented: `-sm row` fails with "device RPC0 does not support split buffers".

models that do not fit one board (flint, Qwen3.5 Q5, Ripple IQ3_XXS), and pp latency halves.
Expert-parallel MoE (each board holds half the experts, tokens routed over wire) is a
special case of row-split for MUL_MAT_ID.

Wire budget on 1 GbE (~110 MB/s), 2-node ring all-reduce traffic ~= tensor size per layer:

- h2048 models (Qwen3.5/flint): 4 KB BF16 per layer per token; 40-49 layers -> ~160-200 KB
  per token -> bandwidth ceiling ~550 tok/s. Bandwidth is NOT the limiter.
- Per-layer sync RTT is: ~40-49 round-trips per token; at ~50-100 us LAN RTT that is
  2-5 ms/token -> tg ceiling ~200-500 before compute. 2.5GbE + jumbo frames + multi-slot
  batching (overlap request A's all-reduce with request B's compute) amortize it.
- Ripple h5120: 2.5x heavier wire; still feasible at tg ~12-30.
- pp512 on h2048: 512 x 4 KB x 40 layers ~= 80 MB per ubatch -> ~0.7 s wire at 1 GbE vs
  ~0.2 s compute -> pp needs Q8_0 wire + compute/transfer overlap (6.1) or stays
  layer-split. Hybrid split modes per phase are not supported today.

Large effort; do after the cheap wins. RDMA transport exists upstream (GGML_RPC_RDMA,
ggml/src/ggml-rpc/CMakeLists.txt:25-44) but needs RDMA NICs - not practical here.

**Scope assessment (2026-11-19): DEFERRED pending user decision.** Split buffers exist
only in SYCL/Hexagon (~400+ lines: split buft, per-split init/set/get) plus CUDA's own
path; RPC would need that whole layer PLUS cross-server reduction orchestration (the
existing COMM_INIT/ALLREDUCE is server-internal; two separate servers need a client
bridge or server-to-server links, upstream #8032). Multi-day effort. Meanwhile the
measured 1GbE economics are poor: layer-split already delivers tg 83 (gemma4) / 69
(Qwen3.5) with ~2 boundary crossings per token; row-split needs ~2 crossings PER LAYER
(30-49 layers) -> at the observed ~0.6 ms per crossing that is 18-36 ms/token overhead,
i.e. a tg REGRESSION vs layer-split on this interconnect. pp would stay wire-bound.
Recommendation: skip row-split until a faster interconnect exists; spend effort on
single-board fit (quants/REAP) and speculation instead.

Verdict: row-split on 1GbE REGRESSES MoE tg and barely helps huge dense; multi-day

revisit only with a faster interconnect. (Async copies don't fix this: per-layer reductions are serial
